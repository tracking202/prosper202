Release notes

Version 1.9.77
-- Changed: The REST API refuses a request body's field instead of skipping it. Every write answers 422 naming the field for a key that is not a field of the resource (the error lists the writable ones), a read-only key (primary key, owner, version, etag) on a create, a null for a column that cannot be NULL, a whole-number field given anything else ("1.5", "1e3" and a 20-digit string were stored as 1, 1000 and PHP_INT_MAX), a number outside its column's range (every such refusal names the range) and a string longer than its column (a strict-mode 500 before); a null is written as NULL where the column takes one. A GET body sent back with PUT is accepted on every resource, SKAN encodings and rotator rules included: read-only keys are accepted with the record's own values, and a version or etag that differs is the 409 an If-Match gives. bulk-upsert rows meet the same rules with field_errors in each error row, an update with nothing left to write is reported skipped, and a bulk body that is an object with keys other than rows is refused. Every hand-written handler (Update, Settings, the Setup variables and pixels, goals, events, conversions, sync, rotators, users, LTV and the rest) refuses the keys it does not read. `p202 import`, `sync` and `diff` leave out the server-set keys (version, etag, landing_page_id_public, a rotator's auto_monetizer and rules); an export imported by an older CLI is refused for them
-- Changed: Objects and lists inside a request body are checked as strictly as its top level, and a refusal names its place (items.0.unit_pirce, customer_crm.country, aliases.0.tpye, events.1, prune_denylist.0, source.nmae). Each of these answered 2xx: on POST /conversions a line item's misspelt unit_pirce stored the line at 0, a unit_price of "abc" stored 0 and customer_crm's unknown keys were dropped; on POST /ltv/revenue an item's qty stored one unit and a country of "United States" was a 500; POST /ltv/customers stored a misspelt alias type as a custom alias, an alias or custom-field value given an object was stored as "Array", and on POST /ltv/events a customer_crm that is not an object read as none; "events": "revenue.recorded" (a string, not a list) subscribed a webhook to every event; an integration's config [1,2,3] was stored (it must be an object, and an empty one is served back as {}); a custom field's options kept a non-text choice as "Array" and were dropped from a text field; and on POST /sync/jobs a misspelt source key was dropped and "prune_denylist": "campaigns" protected nothing from a prune. Rotator rules refuse an unknown key inside a criterion or redirect (redirects.0.weigth stored the redirect at weight 100). A list entry is named field.<position> everywhere: POST /events answers events.1.event_id where it answered events[1].event_id, POST /goals/evaluate goals.0.versions.1.version, POST /conversions/subids subids.1
-- Changed: Numbers and switches that handlers read from a body themselves are read strictly, a 422 naming the field (and its range) where a cast used to guess: on POST /conversions click_id "12abc" recorded the conversion on click 12 and conv_time "2026-10-07" dated it in 1970; LTV merges took source_customer_id or source_company_id "12abc" as record 12, and an LTV occurred_at of "2026-10-07" was 2026 seconds; a rotator public_id "abc" silently took a generated id; a sync job's max_attempts and the sync worker's limit were clamped. A sync job's flags (force_update, skip_errors, dry_run and the rest) and a custom field's is_required take true/false, 1/0 or their strings and nothing else: "false" read as true, so a job sent force_update, skip_errors and dry_run as "false" was queued with all three on, and is_required "false" made a required field. A subscription's started_at, amount and interval are read to their columns ("2026-10-07" was stored as 2026 and an amount of "abc" as 0), the amount is required on an upsert, and a period end past 2106-02-07 is refused instead of a 500
-- Changed: time_from and time_to on GET /reports/*, /clicks, /conversions, the LTV reads and GET /attribution/reports/breakdown take unix seconds, a date (YYYY-MM-DD: time_from from its first second, time_to through its last, in the account's time zone) or a time with its offset (2026-10-01T09:30:00Z). They were cast to integers, so 2026-10-01 meant 2026 seconds after 1970 and the answer covered all time with nothing said; milliseconds (named as such), a day that does not exist, a time without an offset and a range whose start is after its end are now a 422 naming the field. 0 still means no bound. `p202 ltv` passes the window as given; `p202 attribution` still takes unix seconds only
-- Changed: Query parameters are applied or refused, never ignored or clamped. GET /reports/* refuses an unknown parameter, a list or a malformed value (campain_id=7 answered for every campaign), a breakdown sort that is not a metric column (it became total_clicks), and a sort_dir, limit or offset out of range; GET /clicks took three ids and a window and ignored everything else (keyword=shoes listed every click), and now refuses what it does not take. Every CRUD list, conversions, rotators, the sync change feed, its audit log, the error log and the LTV reads take their whole-number parameters (limit, offset, cursor_ttl, from_epoch/to_epoch, the LTV reads' days and months, and updated_since where it is taken) only in the documented range, or answer 422 naming the parameter and the range (limit=1000 answered 500 rows that read as all of them, limit=abc one row, updated_since=yesterday every row). A CRUD list's filter[...] on something it cannot filter by is a 422 naming what it does filter by (filter[aff_campaing_id]=3 answered every row), and read-only fields and the id are now filterable. GET /ltv/customers refuses an unknown sort or dir (it ranked by total revenue instead), the other LTV choices (segment, by, status) name the parameter and its values in field_errors, and GET /audit/sync-jobs refuses an unknown format or status (it answered JSON, or an empty list)
-- Changed: "0" is a value, not an absent parameter. GET /ltv/summary, /ltv/customers, /ltv/breakdown and /ltv/predict refuse period=0, which answered over the default window as though that were the one asked for; GET /conversions?campaign_id=0 is a 422 where it listed every campaign's conversions (as `p202 conversion list --aff_campaign_id 0` sent it), and so is a non-number, which listed none; a CRUD list's cursor=0 is refused as every other malformed cursor is; and on POST /conversions a given customer_id must be a positive id, while a customer_ref of "0" now reaches the customer lookup instead of being dropped
-- Changed: An id in a REST path is read strictly: anything but the digits of a positive whole number is a 404 `Not found: "1e3" is not an id`. Every route cast the segment, so DELETE /campaigns/2e0 deleted campaign 2 (and its dry run previewed it), PUT /aff-networks/2x renamed category 2 and GET /aff-networks/2abc read it
-- Changed: ?dry_run=1 on a POST, PUT or PATCH previews or is refused, never ignored. The Update routes and POST /system/retention/delete-before preview; every other write answers 422 "This route has no preview; remove dry_run to perform the write." before anything runs, where the parameter was ignored and the write ran (POST /aff-networks?dry_run=1 created a category). A misspelt dry_run value is a 422, and dry_run beside staged is refused on any write
-- Changed: updated_since on a list is taken only where the records keep an update time (GET /forecast-events) and is a 422 elsewhere, pointing at GET /changes/{entity}, which takes it; deleted_since is a 422 on every list, which answers live records only. The lists looked for those columns with a statement the database will not prepare, so neither filter could work. A server-side sync job's body may not carry updated_since (send "incremental": true): an incremental job reads the source whole and skips unchanged records by its manifest, and sends no time filter
-- Changed: A date field (a forecast event's event_date and end_date) takes a real day written YYYY-MM-DD or is a 422 naming it; "", 2026-02-30, 27/11/2026 and a time answered 500. A date that may be empty is cleared with null, which `p202 forecast-event update --end_date ""` now sends (it sent "", the 500), and the CLI checks date flags before any request. filter[event_date] with something that is not a date is a 422 instead of an empty list
-- Changed: The REST API answers money and counts as JSON numbers rather than MySQL's decimal strings: the summary, breakdown and timeseries reports' metrics (an empty summary answers 0 where it answered null), a record's DECIMAL fields (a campaign's payout, a tracker's CPC), GET /clicks, /clicks/{id}, /clicks/{id}/conversions and /conversions, the LTV summary and /ltv/cohorts. A record's version changes once with this, so a client holding an older one gets the documented 409 and re-reads. POST /clicks/cpc's cpc and a revenue upload's totals stay exact decimal strings. The Go CLI reads a number or an older server's string alike, and its tables keep up to four decimals for an amount finer than cents
-- Changed: An API key is held to its user's role as the pages hold that user. Setup records (campaigns, categories, traffic sources and their accounts, trackers, landing pages, text ads, redirectors and their rules) need access_to_setup_section to read or write, GET /trackers/{id}/url and the Mobile Apps reads included (the install token stays open), and a delete needs the record's remove_* permission as well, checked first; a dry run and a staged write are refused as the write is, and a staged change is applied under the applier's current role. A Campaign viewer's key could create, change and delete all of them. Reports, rotator stats, clicks and conversions stay open to every role, but for a role without access_to_campaign_data the absolute clicks, click-throughs, leads, income, cost and net (and a click's or conversion's cost and payout) are null, the ratios kept, beside masked: true, as Overview and Analyze show them. POST /conversions needs access_to_update_section, and DELETE /conversions/{id} delete_individual_subids as well. /system/version, db-stats, cron, errors, dataengine and metrics need access_to_settings beside Admin, as the rest of /system does
-- Changed: Every /goals route needs access_to_setup_section, reads, validate and evaluate included, as Setup › Campaigns and Setup › Mobile Apps do; creating, editing, archiving or re-evaluating a goal that is not a campaign's (an app's or the account's) also needs manage_attribution_models. For a role without access_to_campaign_data a goal's payout and value.amount, and an outcome's value, are null beside masked: true. A Campaign viewer's key could create a paid goal, set its payout and re-evaluate past clicks
-- Changed: Your own preferences, API keys and time zone need access_to_personal_settings, which Personal Settings asks for before showing them: GET and PUT /users/{id}/preferences (which hold the account's integration secrets, privacy setting and tracking domain), the API key routes and their delete preview, and a PUT /users/{id} that changes your own user_timezone. user_active, like user_name, needs a user you may manage, yourself included. Your email and password stay yours to change
-- Changed: /users keeps Account › User Management's rules. An Admin could make itself Super user (POST /users/<self>/roles {"role_id":1}), mint a key for user 1 and set user 1's password. Another user's profile, password, API keys, identity key and preferences now need Admin, user 1's only user 1, and an Admin or Super user account add_edit_delete_admin as well; role 1 is never granted, role 2 only by a Super user, and user 1's roles are fixed; a delete needs add_edit_delete_admin and never removes user 1 or yourself. Changing your own password needs current_password, and passwords are 8 to 72 characters. A user can be renamed (`p202 user update --user_name`) under the page's rule; a name or email another account has is a 409 or 422 instead of a database error, user_timezone must be a zone PHP lists, and user_active must be 0 or 1 ("abc" deactivated the account). `p202 user update --set-password` reads the new password without echo (and --current-password the current one), and `user create` reads the password from piped stdin and takes --user_active
-- Changed: A deactivated user's API keys are refused on v1, v2 and v3 with a 401 saying the account is deactivated; the key lookups checked only that the user was not deleted, so a user switched off in Account › User Management kept every key, with their role. The Go CLI's hint for that 401 names `p202 user update <user_id> --user-active 1`
-- Changed: A Setup record created or updated through the API may link only to the caller's own live records: a category, campaign, landing page, text ad, traffic source, traffic source account or redirector of another account, or one removed, is a 422 whose field_errors name the field and the list route that has valid ids. The API took every id as sent, so a key could file its campaign under another account's category or build a tracker on another account's campaign and read its name back. 0 means none where the link is optional, and aff_campaign_id 0 is still taken where Setup stores it: an advanced landing page, and a tracker that names a redirector or an advanced landing page. An update re-sending a link the record already holds is not checked again, so a record whose campaign was removed can still be saved whole. bulk-upsert error rows carry field_errors, and `p202 import` of another account's export is refused row by row (`p202 sync` maps the ids)
-- Changed: GET /trackers/{id}/url answers the link Get Links builds: on the caller's tracking domain (a domain stored without a scheme takes the request's; with none stored, the host the request used, where it answered 404) with the install's directory, then t202id, the traffic source's live custom variables (from the account's own source only), each built-in token given a value, and t202kw; a landing page's variables go before its #fragment. The tokens are query parameters (c1-c4, utm_*, t202ref, t202b, t202kw), and an unknown parameter or a value holding &, #, ?, whitespace or a control character is a 422; it used to append fixed placeholders (c1={c1} to c4={c4}) no traffic source fills. `p202 tracker get-url`, `create-with-url` and `bulk-urls` take a flag per token, checked before any request, and when create-with-url creates the tracker but cannot fetch its link the hint names the tracker_id and `get-url`
-- Changed: A tracker made through the API takes its campaign's cloaking (click_cloaking -1, as Get Links does) unless told otherwise, and click_cloaking accepts only -1, 0 and 1 as sent ('0.5' and '1e0' were cast). A CPC and a CPA in one request is a 422, an update that sets one switches the tracker to it and clears the other (a CPC tracker given a CPA was charged per click and per action), and a cost outside 0 to 99.99999 is a 422 rather than a database error. tracker_id_public, the t202id in a link, is a 422 when another tracker in any account holds it, and the API and Get Links draw only free ones: a shared id made each click an arbitrary pick between two trackers. Existing shared ids are left as they are
-- Changed: The /rotators API checks a destination and a rule whole before writing anything. A default or a rule redirect is exactly one of a URL (http or https), a campaign or a landing page of the caller's that is not removed; criterion types are the ones the redirects evaluate, with is or is_not; a country is written as the redirects read it ("United States(US)"; a bare US never matched); weights are 0 to 100; and an ip value is a list of single addresses, stored in canonical form, anything else (a typo, a range) refused naming criteria.N.value. A rule update refuses a malformed entry instead of skipping it and writing the rest. Setting a default replaces the whole default and clears the auto-monetizer, as the page does (a default_url set beside an old default campaign was never used), and reads return auto_monetizer. A GET body sent back with PUT changes nothing it only restates: an auto-monetizer default stays, and a removed campaign the rotator or a rule already names is taken as it is, while naming a removed campaign anew is refused. `p202 rotator rule-create` takes --status
-- Changed: POST /conversions refuses what it used to record wrongly or drop with a 2xx. A transaction id the click already has, sent with another payout, conv_time, customer or line items, is a 422 naming transaction_id (it answered 201 duplicate: true and dropped the second sale); the same request still replays, and pixels and postbacks keep the first. items or customer_crm with no customer to attach them to (none named, none linked to the click, none from the account's customer c-param) is a 422 naming each, with nothing written and the Idempotency-Key unspent (it recorded the sale without them); gpb.php, gpx.php and upx.php keep the conversion and log the line items they did not store. A reversal_id without status "reversed" is a 422 (it recorded a new sale). transaction_id and reversal_id must be a string or a JSON integer (a very large integer arrived as a float, so two orders collided; an object was stored as "Array"), at most 255 bytes (a 500 before), and the payout must fit the ledger's decimal(11,5) (a 500, or 999999.99999 stored). `p202 conversion import` compares the payout and time of a row whose transaction id the click already has: a difference is the status conflict, not sent, exit 5, where it was reported duplicate and dropped
-- Changed: The LTV writes say what they did. POST /ltv/revenue with a used idempotency_key and another amount, customer or line items, and a subscription event resent under its key or transaction id with another amount, are a 422 naming the key and what differs (they answered duplicate: true or changed: false and recorded nothing). POST /ltv/webhooks refuses an event name this install never sends, naming events.N with the five it sends and "*" (revenue.recoded made a hook that heard nothing, 201). Every LTV 422 names its field in field_errors (amount, items.0.quantity, custom_fields.tier, ...), a repository's own failure is a 500 rather than a 422, and deleting a company with customers attached is a 409. customer_ref must be a string and customer_ref_type one of its list (an object made a customer named "Array"), and POST /ltv/revenue's external_ref and transaction_id are at most 255 characters and idempotency_key 191
-- Changed: GET /reports/*, the LTV reads and the attribution reports count periods in the account's time zone, as the report pages do: today and yesterday from the account's midnight (they used the server's), and last7, last14, last30 and last90 as today so far plus the N whole days before it (they were N×24 hours to the second, up to a day less than the page's Last N Days). Timeseries buckets, daypart and weekpart are the account's days and hours too: timeseries grouped in the database connection's zone, and daypart and weekpart fell back to UTC hours without a word on a server without MySQL's time-zone tables; timeseries now says which zone. The CLI's --days N stays a rolling N×24 hours
-- Changed: An account's time zone is one rule on the pages and in the API: a zone name PHP lists, the backward-compatible names (Europe/Kiev) included, spelled as listed; anything else reads as UTC. A stored offset such as +05:30 counted UTC days on the pages while the API grouped by the fixed offset; it is UTC in both now. Personal Settings offers the account's own zone first and selected, so a backward-compatible name is no longer replaced by Africa/Abidjan when the page is saved for another reason, and PUT /users/{id} accepts such a name, so the account's own GET body goes back
-- Changed: /capabilities' server.timezone_support is always named-timezone: every report converts times with PHP's zone database, so whether MySQL has zone tables no longer matters, and fallback-only and unknown are no longer sent
-- Changed: PUT /users/{id}/preferences holds every value to the rule of the page that owns it and refuses an unknown key with a 422 naming it (it was dropped with a 200). user_daily_email is "" (never) or an hour 00-23; the "off" the docs suggested failed the column. It also writes what the pages write that it could not: the keyword, referer, cost source, privacy and ad settings, the ClickBank, Zaxaa and JVZoo keys (a changed cb_key resets its verification) and the four LTV settings; chart_time_range is now the Overview chart's own setting (it was written where nothing reads it). A currency change re-prices every campaign's payout, as Personal Settings does, fetching the rates first: a rate the service does not give is a 502 and nothing is written. `p202 user prefs update` has a flag for each column, checked before any request (--user_daily_email never)
-- Changed: The Go CLI reads a masked answer for what it is: a table or CSV of one prints a note on stderr, --ndjson lines carry "masked": true (click and conversion list --all and click list --follow too), and --json shows it as sent. Commands that compute from the hidden figures (campaign optimize, report losers and winners, forecast, analytics --split-at, list --with-stats, report summary --all-profiles) refuse it with exit 2, naming the permission and `p202 whoami`, instead of reading nulls as zeros, and so do report breakdown's --min-clicks, --min-cost, --zero-leads and a --having on a hidden figure; a filter on a ratio still runs and keeps the flag
-- Changed: The Go CLI no longer exits 0 for what did not happen. A confirmation nobody can answer (no terminal and stdin at its end: an agent, a script, a pipe) is a validation error, exit 1, saying nothing was done and naming --force (and --dry-run where the command has it), where it printed "Cancelled." and exited 0; an explicit no still cancels with exit 0, and `user apikey rotate` keeps the old key and says so. `p202 import` and `p202 sync` with --skip-errors exit 5 when any record failed, and a 401 or 403 stops them; a server-side sync job that ends failed, partial or cancelled exits 5. `report breakdown` refuses a --having it cannot read ('roi<abc', a field no row has, NaN) with exit 1, where it dropped the filter or read the field as 0

-- New: The Setup section's code and per-source settings have an API and CLI commands, so an agent can finish a landing-page tracker or a conversion setup without the web UI. GET /landing-pages/{id}/code (`p202 landing-page code <id>`) answers Get LP Code's loader script and outbound links, for a simple page or for each of an advanced page's offers (?offers=campaign:12,rotator:3, `--offer`), byte for byte the page's (both build them with Prosper202\Setup\LandingPageCode, on the caller's own tracking domain as the pages read the signed-in user's, or with none stored on the host the request came in on). -- New: The UI's Update section has an API and CLI commands. POST /clicks/cpc sets what past clicks cost (`p202 click update-cpc`): a dry run counts the clicks and names the highest click id, and the write runs only if those clicks still number the same, so a click recorded after the count is never changed. POST /conversions/subids marks subids converted (`p202 conversion mark-subids`), /conversions/subids/delete clears them (`delete-subids`), /conversions/subids/reset clears a category's or campaign's (`reset-subids`), and /conversions/uploads records a revenue report as a batch whose values replace earlier uploads' (`upload-revenue`, columns read from the header or named). Each runs the page's own code, asks for the role permission the page asks for (access_to_update_section, and delete_individual_subids to delete subids), takes ?dry_run=1, and says how much stands when it stops part-way. The sums and the lines are listed for the first 1,000 of each, with counts of the rest, so a report of the 8 MB the route takes answers in kilobytes, and a preview reads the report twice rather than holding it, within PHP's default 128 MB. update-cpc, delete-subids, reset-subids and upload-revenue check first and ask before writing (--force skips the question, never the check); mark-subids, like its page, asks nothing (--dry-run previews); all five refuse --staged

-- New: `p202 report losers` and `p202 report winners` take --payout, your revenue per conversion (an average order value). Each row's break-even CPC is the payout times that row's own conversion rate. Without a break-even, losers only listed rows with spend and no conversions, so a traffic source that made some sales at a loss was WATCH and never listed, and the starter check never saw it. The only payout input was --aff_campaign_id, which also filters the report to that campaign and so turns the attribution check off. --payout adds no filter, so those sources come back CUT, or TEST when they start sales. It values every sale the commands report: total_net is conversions × payout less cost (so winners lists a row that is profitable at your payout even when the campaign's recorded income puts it at a loss, and each row says the payout it was valued at), and the first-touch ROI of the attribution check is attributed conversions × payout against cost. The classic report counts a converted click once however many sales it had (accumulate-mode campaigns, repeating goals), so the check also reads the Last touch model, whose credits count each row's sales, and values the rows it reads per sale: a loser that covers its break-even once every sale counts is dropped (a note says how many), and a source that is profitable only through repeat sales is listed as a winner, also on an account with no First touch model (the closer check is then skipped, but sales are still counted). Without a Last touch model, or when the check can't run, sales are counted per converted click and a note says so. --max-cpc still sets the break-even when both are given, and an explicit --payout of 0, a negative or non-finite one, or one over 1,000,000,000 is refused with exit code 1 before any request

-- New: Goals. A goal is a named outcome — an install, an event (with conditions on its properties if you like), the Nth occurrence, a running sum, a step after another goal, within a window — and what reaching it is worth. A goal belongs to a campaign, an app registration or the account, and web campaigns and both app platforms share the same goals. Every edit is a new version and a conversion keeps the version that produced it; re-evaluation previews, then applies, a version to past clicks and installs. A campaign pays for a goal at its own payout, and an untrusted value (revenue reported by p202.track(), say) is recorded but never paid. Credential fields are matched by substring, so preference writes carrying ipqs_api_key or a Slack incoming webhook are refused too, as is deleting an API key, which addresses the key by its own value in the request path
-- Fixed: Applying a staged change now requires write scope for the area the change touches, as documented, instead of a scope token no key could hold; granular approver keys (for example read,campaigns:write) work again

-- Fixed: A create that writes its row and then fails on a later step is no longer reported as a failed create; the API says the record exists and must be looked up rather than retried, and neither an Idempotency-Key retry nor re-applying a staged change can duplicate it
-- Fixed: The number of staged proposals awaiting a decision is now capped per user (P202_STAGED_CHANGE_MAX_PENDING, default 1000); staging past the limit is refused with a message naming what to resolve first, instead of letting one account's queue grow until every stage and list slows down
-- Fixed: An API key whose scope value cannot be read (truncated or empty JSON in the column) is no longer treated as full access; it now authorizes nothing and the refusal names the unreadable value so the row can be found. Keys with no scope at all still mean full access, as before

-- Fixed: `p202 sync --staged` is refused up front instead of silently falling back to a client-side sync that records proposals while reporting them as synced records

-- Fixed: A staged change that is mid-apply is no longer eligible for retention pruning, so its audit entry survives for the handler that is about to complete it
-- Fixed: Two workers racing the one-time move of the v3 API state directory no longer end up on different directories; the worker that loses the race now uses the moved directory instead of recreating the old one and writing state nothing reads
-- Fixed: A staged change whose apply process died mid-dispatch is closed as apply_interrupted instead of being stuck in applying forever — it is never silently re-applied, since the interrupted write may already have landed; a corrupted stored payload is reported rather than applied as an empty write
