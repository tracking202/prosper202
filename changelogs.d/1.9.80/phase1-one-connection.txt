# Click throughput, phase 1: fewer database connections per click, and lost clicks counted.
-- Changed: A click on a new install opens one MySQL connection, not two. 202-config.php opened a read connection beside the primary on every request, though only Analyze › Spy reads through it, so under load Apache's workers asked MySQL for twice as many connections and every refused connection was a click sent on without being saved. The config written from 1.9.80 opens the read connection the first time something reads through it (none at all when the replica setting names the primary's server, and the primary when the replica cannot be reached, logged). A 202-config.php written by an earlier release keeps working and still opens both: the click scripts close its read connection as soon as it is open, and when MySQL refuses that second connection, the click script opens the primary alone once more and saves the click on it, unless that is refused too. The signed-in pages no longer open the read connection either, except Spy.
app: Changed: A click on a new install uses one database connection instead of two, and on an upgraded install a click is still saved when MySQL refuses the second connection, so a busy tracker loses fewer clicks to MySQL's connection limit.
-- New: Clicks redirected without being saved are counted. When the database refuses the connection (too many connections, or down), dl.php, lp.php and off.php still send the visitor to the URL they keep for an outage, and the click is lost; each one is now counted in 202-config/temp/unsaved-click-redirects.json on the web server, with the first and last times, shown on Account › Settings, GET /api/v3/system/info (unsaved_click_redirects) and 202-cronjobs/health.php. A last one in the past 7 days adds a warning to each, and the unauthenticated GET /api/v3/system/health says only that there is one (unsaved_click_redirects.state ok or warning), never the count. The count never holds a visitor up: one that finds another being written waits about 30 ms and is then dropped, so under contention it can come out low. Each web server or container keeps its own count, and one redeployed without 202-config/temp/ starts again. When the web server cannot write 202-config/temp/, nothing can be counted, and the state says so (unrecordable) with its own warning, rather than reading as none. rtr.php, offrtr.php and a click answered 503 because no URL was kept for an outage still lose their clicks uncounted.
app: New: Account › Settings says how many clicks were redirected without being saved while the database was out of reach, or that they cannot be counted on this server.
-- Changed: Docker: Apache's KeepAliveTimeout is 2 seconds (it was 5, which held every worker idle at 30-40 clicks per second) and MaxRequestWorkers is set at 150; the compose files' MySQL runs with max_connections 400 and the binary log off, which also ends point-in-time recovery from the binary log (documentation/deploying-on-coolify.md). An existing Coolify deployment keeps its MySQL settings until its compose file is changed. innodb_flush_log_at_trx_commit=2 is documented as an opt-in.
