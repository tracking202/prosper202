-- New: A global postback (tracking202/static/gpb.php) whose SubID was not filled in can still record its conversion. When subid (and sid) is empty or arrives as the network's unfilled macro and nothing else ([[subid]], {aff_sub}, {{name}}, ${name}, [name], [=SID=], #s2#, %subid1%, <name>), the postback was answered "SubID not found" and the sale was lost. It now finds the click by an ad click id the postback sends back: gclid, gbraid, wbraid, msclkid, fbclid or ttclid under its own name, or in a parameter of the network's own naming that the account lists under Personal settings › Advanced › Match conversions by ad click id (user_pref_click_id_params on PUT /users/{id}/preferences, `p202 user prefs update --user-pref-click-id-params`, `bin/p202 user:prefs:update --user-pref-click-id-params`), whose value is tried as every kind of id among that account's clicks only. Pass the id to the network in a sub id slot ([[gclid]] in the campaign URL) and have it sent back. The id is compared exactly (case included), among clicks visited in the last 30 days. An ad click id names one ad click, so when several clicks carry it (a reloaded landing URL makes two) and all are one account's, on one campaign, from one traffic source account, the conversion goes to the latest of them by its last visit, or to the one that already holds the sale's order number or event, so a retry is a duplicate and not a second sale; clicks on more than one campaign, traffic source account or account are answered 409 and record nothing, and when they are all one account's, that account's Inbound Log says which. A value no platform issues (undefined, null, (not set), an unfilled __GCLID__) is not looked up. Until the upgrade has run, a postback that needs the lookup is answered 503 with Retry-After. The click's account's postback authentication applies as it does to a SubID. A SubID that is there is read exactly as before, and one that names no click is still refused. The conversion is recorded with the new match method ad_click_id (GET /conversions?match_method=ad_click_id, the match-methods breakdown, Group Overview, Visitors and both CLIs), which the offline conversion files and the ad platform destinations treat as a click the conversion named, and Setup › Inbound Log says which parameter found the click or why none was found. The lookup reads a new table, 202_clicks_ad_ids, which says which clicks carry each id: the click path writes it with the click, click deletion removes it with the click, and the upgrade fills it for the clicks visited in the last 30 days in short statements, so clicks keep being recorded while it runs. Only gpb.php does this.
