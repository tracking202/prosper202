-- Fixed: A server-side sync job that had ended could be written over. Cancelling a job (POST /sync/jobs/{id}/cancel) read it, decided, and saved the copy it had read: when the job's run finished in between, the cancel replaced `succeeded` (or `partial`, `failed`) and the run's results with `cancelled`, counted the job twice and wrote it a second audit record. The same happened to a job another host had taken as lost while its run went on, and a failure after a job's end was saved (the audit file could not be written) put a sync that had succeeded back in the queue to run again. A job's status now changes in one place, which reads the job again under its lock and makes only the moves the lifecycle holds: queued to running, cancelled or failed; running to succeeded, partial, failed, cancelled, or queued again for another try. succeeded, partial, failed and cancelled are final, each with one audit record (a run that failed after a cancel was asked had none). A cancel that arrives as the run finishes answers the job as it ended, and a try that stopped before it started (its pair was busy) leaves a job that another host sharing the state directory started in between as running, where it had put it back in the queue under that run.
app: Fixed: Cancelling a sync job as its run finished could replace the run's result with "cancelled" and record the job twice.
-- Fixed: POST /sync/jobs/{id}/run started a job that already read `running` whenever nothing on that host held its lock: a second run beside the first on a server that shares its state directory with another host, or a second pass over what a killed run had half written. Only a queued job is started; a running one is answered as it stands and is failed as `sync_worker_lost` once its run's time has passed, as before.
-- Fixed: Two requests to queue a sync job under one Idempotency-Key, arriving together, both found the key unused and both queued a job. The key is now taken in one step with reading it: the second request is a 409 (`idempotency_in_flight`) until the first has answered, then replays its job.
-- Fixed: `p202 sync` printed the reply to queueing the job and exited 0 when its 20 checks ran out before the job ended, so a job whose first try had failed and was waiting for its next read as a sync that happened. A job still queued is now exit 5, with the job as it stands on stdout and an error naming it and `p202 sync history`; a job still running is a warning on stderr naming it, with the job as it stood (`"status": "running"`) on stdout.
app: Fixed: `p202 sync` no longer reports success when the server-side job it queued has not finished.
