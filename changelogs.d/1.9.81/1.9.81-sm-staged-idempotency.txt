-- Fixed: A staged change whose apply ran past 15 minutes was closed as apply_interrupted by the next caller, and the first process then overwrote that when it returned: a failed dispatch put the change back to `staged`, where a second apply could run a write the operator had already been told to check and stage again. A change closed as interrupted now stays closed; the late process records `applied` only when its write landed, and otherwise leaves what it learned in last_error. A staged change's status is now one transition table (StagedChangeStatus), and the state store refuses any status change the table does not hold. GET /staged-changes documents the apply_interrupted status filter.
app: Fixed: A staged change closed as interrupted is never put back on the queue by a slow apply that fails late.
-- Fixed: POST /{resource}/bulk-upsert read its Idempotency-Key before writing and recorded the answer after, so a retry that raced the first request found nothing and stored the batch a second time, and a failure between the rows and the record left the key free for the same. The key is now claimed before anything is written: a retry sent while the first request runs gets 409 idempotency_in_flight; a request that fails with nothing stored frees its key; one that stored rows and could not record its answer spends the key (409 idempotency_indeterminate) instead of running again.
app: Fixed: A bulk-upsert retried while the first request was still running could store its rows twice.
-- Changed: An Idempotency-Key record that holds a response, or is marked as unknown, is no longer overwritten or freed: the response of a second run of the same request is logged and the first one keeps being replayed.
