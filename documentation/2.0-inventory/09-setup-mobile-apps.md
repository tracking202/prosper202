# Setup: Mobile Apps

Setup › Mobile Apps is where an account registers its iOS and Android apps for app-install attribution and sets each one up. It is one URL, `tracking202/setup/mobile_apps.php`, with four views chosen by the query string: the list (with the Register panel and the iOS receiver checks), the edit form (`?edit=ID`), the iOS app page and the Android app page (both `?app=ID`, chosen by the registration's platform). Registration takes one field: a store link, a bare App Store id or a package name is parsed into platform and key, and the name and icon are looked up from the App Store or Google Play. The iOS page holds the SKAdNetwork / AdAttributionKit conversion-value rules (with a starter schema), the app's goals, the store link builder and the SDK setup with recent postbacks. The Android page holds the link builder (store link with the install token), the SDK setup with recent installs, the goals with an install funnel, and Play Integrity. The page is a server-rendered form: every POST is handled by `tracking202/setup/MobileAppsController.php`, which calls the v3 controllers in process as the session's account (`$_SESSION['user_own_id']`), then redirects back with a flag that selects a flash message (POST, redirect, GET). The page loads `202-config/connect.php`; the base class `tracking202/setup/_base/SetupController.php` calls `AUTH::require_user()`, then needs `access_to_setup_section` (refused: `location` to `tracking202/` and `die`, no message). Every change also needs `manage_attribution_models`. Every POST checks the hidden `csrf_token` field with `AUTH::csrf_token_matches()`.

| Page | Path | Permission |
|---|---|---|
| Mobile Apps: list and Register panel | `tracking202/setup/mobile_apps.php` | `access_to_setup_section` to view; `manage_attribution_models` to register, edit, remove or accept test signals |
| Mobile Apps: edit app | `tracking202/setup/mobile_apps.php?edit=ID` | `access_to_setup_section`; the form is rendered only with `manage_attribution_models` |
| Mobile Apps: iOS app page | `tracking202/setup/mobile_apps.php?app=ID` (iOS registration) | `access_to_setup_section` to view; `manage_attribution_models` for every form on it |
| Mobile Apps: Android app page | `tracking202/setup/mobile_apps.php?app=ID` (Android registration) | `access_to_setup_section` to view; `manage_attribution_models` for every form on it |

Menu: Setup sub-menu (`tracking202/_config/sub-menu.php`) entry "Mobile Apps". The Setup strip is empty for roles without `access_to_setup_section`. With the seeded roles, Super user and Admin have both permissions; Campaign manager has `access_to_setup_section` and `view_attribution_reports` but not `manage_attribution_models`, so it sees the pages read-only; Campaign optimizer, Campaign viewer and Publisher do not reach the page.

Shared behaviour of all four views:

- **Page shell**: `template_top('Mobile Apps - Setup')`, panel header "Mobile App Attribution". Scripts: inline receiver/intake probe and the rule form's kind switch, `p202-setup.js?v=2` (show-when fields, disabling hidden inputs) and `p202-ui.js` (Copy buttons, Reveal/Hide of the masked token, `data-confirm` forms through `window.confirm`, Advanced disclosures remembered in `localStorage` under `p202-disclosure:<name>`).
- **Permission for writes**: `MobileAppsController::requireManage()` throws "You do not have permission to change mobile app registrations." for any POST action from a user without `manage_attribution_models`; the page then renders the list with that message as a flash. A user without the permission sees the warn flash "You can see the registered apps here. Changing them needs the attribution models permission." and no forms or change buttons on any view.
- **CSRF**: every form carries `csrf_token` (from `$_SESSION['token']`). A mismatch raises "Invalid CSRF token", shown as a flash over the list.
- **Errors on POST**: a `ValidationException` puts its field errors under the fields (or, when it has none, its message as a flash); an `HttpException` (conflict, not found) becomes a flash. The posted values are kept to refill the form (`credential` and `csrf_token` are never kept), and the page re-renders the view the form came from: the app page when `registration_id` names one of the account's apps, the edit form for an `update` without `return_to=app`, otherwise the list with the field errors shown as flashes. An `InvalidArgumentException` from anywhere is shown as a flash over the re-rendered GET view. Any other exception redirects to `tracking202/setup/`, which redirects to Traffic Sources (`ppc_accounts.php`) with no message; an exception that escapes the controller redirects to `tracking202/setup/?error=mobile_apps_error`, and nothing reads that flag.
- **Unknown action**: a POST whose `action` is not one of the fourteen below answers the flash "Unknown action."
- **POST actions** (`action` field): `register`, `update`, `remove`, `accept_dev`, `rule_save`, `rule_remove`, `starter_schema`, `rotate_token`, `integrity_mode`, `integrity_credential`, `integrity_clear`, `goal_save`, `goal_archive`, `link_apply`.
- **Ids from the request** are read with `(int)` (`?app`, `?edit`, `?rule_edit`, `registration_id`, `rule_id`), so `12abc` reads as 12. Every lookup is scoped to the session's account by the v3 controller, so another account's id reads as not found.
- **Origin**: the server URL shown in the SDK snippets and the receiver note is `install_request_base_url($_SERVER, get_absolute_url())`, the request's own scheme and Host.
- **Account currency** (for rule revenue): `UsersController::accountCurrency()` for the account owner; USD when the read fails.

### Mobile Apps list: `tracking202/setup/mobile_apps.php`

- **Where / who**: `/tracking202/setup/mobile_apps.php` with no `app` or `edit` parameter. Setup › Mobile Apps. Needs `access_to_setup_section`; the Register panel, the remove buttons, the edit links and the development nudges need `manage_attribution_models`.
- **Purpose**: Check that this install's iOS postback receivers can be reached, register an app from its store link, and list the account's registered apps.
- **Data shown**:
  - **Receivers strip** (iOS): "SKAdNetwork receiver (iOS)" at `<origin>/.well-known/skadnetwork/report-attribution/` and "AdAttributionKit receiver (iOS)" at `<origin>/.well-known/appattribution/report-attribution/`, each with a status pill (starts as "Checking…"), a Copy button, and a note that the bare origin goes into the app's Info.plist. A Re-check button runs the probe again. The probe is client-side JavaScript: when the page's origin is not `https` or has a port other than 443, the pill shows warn "Apple cannot reach this" with a title explaining why, and no request is made; otherwise it does `fetch(url, {method: 'GET', credentials: 'omit'})` and shows "Ready" (any 2xx), "HTTP <status>" (bad) or "Not reachable" (network error).
  - **Register panel** (manager only): heading "Register an app" with a sub-text. See Inputs.
  - **Empty state** (no apps): "No apps registered yet", saying that iOS postbacks that arrive before registration are kept for 30 days and claimed when the app is registered. When some setup is still undone, a "Getting started" checklist of five items; the last item summarises the receivers ("both ready" or "N of M ready").
  - **Your apps** panel: a count pill from `appCountLabels()`: "N app(s)" / "N registered"; when the list was cut, "N of T apps" / "N of T"; when the total is unknown, "first N apps" / "first N shown". The list reads at most 500 registrations (`RegisteredApps::MAX`), the newest 500 by id, then sorts them by name (case-insensitive). Each row: the icon (stored data URI shown as a 20×20 image, else a Bootstrap Android or Apple icon), the name linked to `?app=ID`, a meta line "<platform> · <app_key>", a "test signals on" pill when `accept_test_signals` is 1, and actions Open, Edit (`?edit=ID`, manager) and Remove (manager).
  - **Development nudge** (iOS apps without development trust, manager only): "N development postback(s) have arrived for this app and are not counted. Accept them while you test?" with an Accept button. The count comes from the postback report grouped by registration with `signature = development` for those apps; a failed read shows no nudges.
  - **Flash messages** from the redirect flags: `registered=1` (Android: "App registered, with its built-in install goal. Next: point a campaign at its store link below, and build the app with the SDK and its app token."; iOS: "App registered. Its postbacks are claimed from now on, and any already received were claimed too."; shown on the app page), `already=1` "You had already registered this app. Here it is.", `saved=1` "Changes saved.", `removed=1` "Registration removed. Postbacks it had claimed keep their owner; development trust is withdrawn."
- **Inputs** (Register form, `action=register`):
  - `app_reference` (text, required, autofocus, placeholder a Google Play link; help "Paste the store link. An App Store id or a package name works too."). Parsed by `AppIdentity::fromStoreLink()`: a run of digits or `id<digits>` (App Store id: positive, no leading zero, fits an int); an Android package (two or more dot-separated segments, each starting with a letter, case-sensitive, at most 255 characters); an `apps.apple.com` or `itunes.apple.com` link (path `/id<digits>`, with the slug from `/app/<slug>/id…`); a `play.google.com/store/apps/details?id=` link; a `market://details?id=` link; and the same store hosts without a scheme. Anything else is refused under `app_reference` with the parser's message. Blank: "Paste the app's App Store or Google Play link (or its App Store id or package name)."
  - `app_name` (text, maxlength 255, required): shown only when the store lookup gave no name, with a "decided" line "Read as <iOS|Android> · <App Store ID|Package> <key>" and the field error "<The App Store|Google Play> did not answer, so the name could not be looked up. Type it once and it is saved with the registration."
  - Advanced disclosure (remembered as `setup-mobile-apps-advanced`; open when either field below was posted): `notes` (textarea, maxlength 500, optional) and checkbox `accept_test_signals` (value 1) "Count test signals while testing".
  - Button "Register app".
- **Actions**:
  - **Register** (`register`): parse the reference; look the (platform, key) up among the account's own registrations first, and when found redirect to `?app=ID&already=1` without any store lookup; when `app_name` is blank, look the listing up (`StoreListing::lookUp()`); still no name → ask for it as above; then create the registration (`AppRegistrationsController::create()` with `platform`, `app_key`, `app_name`, trimmed `notes`, `accept_test_signals` 0/1); store the icon; redirect to `?app=ID&registered=1`.
  - **Open** an app: link to `?app=ID`. **Edit**: link to `?edit=ID`.
  - **Remove** (`remove`, `registration_id`): confirm "Remove this registration? iOS postbacks it already claimed keep their owner, and Android installs keep their conversions; its goals are archived and test trust is withdrawn." → delete → `?removed=1`.
  - **Accept development postbacks** (`accept_dev`, `registration_id`, `accept=1`): sets `accept_test_signals` → `?app=ID&dev=1`.
- **Writes and side effects**:
  - Store lookup (`tracking202/Apps/StoreListing.php`): iOS asks `https://itunes.apple.com/lookup?id=<id>` (name from `trackName`, icon from `artworkUrl100`, `artworkUrl60` or `artworkUrl512`; a name from the link's slug when the lookup gives none); Android fetches `https://play.google.com/store/apps/details?id=<pkg>&hl=en` (name from `og:title` minus " - Apps on Google Play", icon from `og:image`). Icons are taken only over https from `*.mzstatic.com` or `play-lh.googleusercontent.com`, at most 40,000 bytes, with the image type checked by its magic number, and kept as a `data:` URI. Names are cut to 255. Curl: 2 s connect, 4 s total, no redirects, pinned to the resolved address (`FixedHostRoute`). `P202_APP_STORE_LOOKUP_ORIGIN` overrides the origin for loopback test servers only.
  - Create (`AppRegistrationsController`): `app_name` required, at most 255; `notes` at most 500; (platform, app_key) unique across every account, so an app another account registered answers 409 "This app is already registered." (shown as a flash). A new registration is created with Play Integrity off and a newly minted `app_token`. Android: the built-in install goal is created. iOS: unclaimed postbacks for that App Store id (`registration_id` NULL, `user_id` 0 or this account's) are claimed, and development trust is synced to `accept_test_signals`. A change record is written.
  - Icon: `AppIcons::store()` updates `202_app_registrations.app_icon` (only `data:image/png|jpeg|gif|webp;base64` values); a failure is logged and the registration stands.
  - Slack: `mobile_app_registered` with `{app, app_id}` and the user name, to the account's Slack integration ("Mobile App: [app] (id [app_id]) Registered by #[user]").
  - Remove (`AppRegistrationsController::delete()`, in one transaction): withdraws development trust, unlinks the app's postbacks (`registration_id` NULL), settles unverifiable installs and orphaned pending clicks, deletes the stored Play Integrity credential, retires and deletes the app's conversion-value rules (history kept with `effective_at`), unlinks campaigns that named the app (`202_aff_campaigns.app_registration_id`), archives the app's goals; then writes change records.
  - Accept development postbacks: an update of `accept_test_signals`, which re-applies development trust to iOS postbacks already received (`signature_state = development`).
- **Edge cases and states**:
  - The "already registered" shortcut works only for the account's own registrations; another account's registration of the same app is a 409 on create, shown as a flash.
  - When neither store answers and the user types a name, the registration has no icon; nothing retries the lookup later.
  - The list shows at most 500 apps and says so in the count pill; icons for the listed apps are read in one query (`AppIcons::forApps()`), and a failed read shows every app with the platform icon.
  - The receiver probe runs in the browser against the page's own origin, so it says nothing about how Apple reaches the server from outside (a reverse proxy on another port, for example) beyond the https/443 check.
  - The Android intake strip is on the Android app page, not on the list.
- **v3 coverage**: GET /apps (list, `limit` up to 500; the name sort is client-side), POST /apps (create; it also accepts `store_link` in place of platform and app_key), DELETE /apps/{id} (remove), PUT /apps/{id} with `accept_test_signals` (accept development postbacks). **MISSING**: the store listing lookup (name and icon) and the icon itself (`app_icon` is not an API field); a lookup of a store reference among the account's own apps without creating (POST /apps answers 409 whoever owns the app); the Slack notice. **PARTIAL**: the development nudge count is GET /apps/report?platform=ios&group_by=registration&signature=development&registration_ids=…, which needs `view_attribution_reports` where the page needs only `access_to_setup_section`. The receiver probes are not v3 routes: they are the public `/.well-known/…/report-attribution/` endpoints, probed from the browser.

### Mobile Apps: edit app: `tracking202/setup/mobile_apps.php?edit=ID`

- **Where / who**: the list view with the Register panel turned into "Edit app" for registration ID. Needs `access_to_setup_section`; the form is rendered only for `manage_attribution_models` (others see the list). The same form (`templates/mobile_apps/_settings.php`) is the Settings panel at the bottom of each app page, posted with `return_to=app`.
- **Purpose**: Change an app's name, notes, test-signal setting and, for Android, its attribution policy.
- **Data shown**: a decided line with the platform and key (not editable); the stored values in each field, or the posted values after a refused save.
- **Inputs** (`action=update`, hidden `registration_id`, `platform`, `return_to`):
  - `app_name` (text, maxlength 255, required); `notes` (textarea, maxlength 500).
  - Advanced disclosure (remembered as `setup-mobile-apps-settings`; open when an Android field below has an error):
    - `accept_test_signals` checkbox: Android "Count test installs", iOS "Accept development postbacks".
    - Android only: `attribution_window_days` (maxlength 3, default 7); checkbox `trust_client_revenue` "Pay goals from the revenue the app reports"; `ctit_min_seconds` "Flag installs faster than, seconds" (default 10); `ctit_max_seconds` (default 86400); `install_cap_per_minute` (default 300); `event_cap_per_minute` (default 200, never below 100); `fast_goal_seconds` (default 5; 0 flags none); select `fast_goal_policy`: `count` "Pay them, and show the flag" (default) or `hold` "Hold them: record, flag, do not pay". The numeric fields are text inputs with maxlength 8 (window 3).
  - Buttons Cancel (back to the list) and "Save changes".
- **Actions**: **Save** → `AppRegistrationsController::update()` with `app_name`, `notes` and `accept_test_signals` (always sent, 0 or 1); for Android also `trust_client_revenue` (always, 0 or 1) and each other Android field only when it is not blank (sent as the typed string). Redirect to `?saved=1`, or `?app=ID&saved=1` with `return_to=app`.
- **Writes and side effects**: the registration row; a change record; the claim and policy are re-applied (iOS: the trusted bit of development-signed postbacks; Android: `InstallIntake::rejudgeTestInstalls()`).
- **Edge cases and states**: API validation, shown under the fields: window and trust "must be a whole number from 1 to 365" / "from 0 to 1"; `ctit_min_seconds` 0–3600, `ctit_max_seconds` 60–31,536,000, `install_cap_per_minute` 1–60,000, `event_cap_per_minute` 100–60,000, `fast_goal_seconds` 0–3600, `fast_goal_policy` `count` or `hold`; a null "cannot be cleared"; `ctit_min_seconds` must be below `ctit_max_seconds`; Android-only fields sent for iOS "applies to Android registrations only" (the form does not send them for iOS). A blank Android field keeps the stored value, so a field cannot be reset to its default except by typing the default. `?edit=` naming a missing or foreign id renders the list with the Register form.
- **v3 coverage**: GET /apps/{id}, PUT /apps/{id}.

### Mobile Apps: iOS app page: `tracking202/setup/mobile_apps.php?app=ID`

- **Where / who**: reached from the list's app name or after registering. Needs `access_to_setup_section`; every form on it needs `manage_attribution_models`. A missing or foreign id renders the list with the flash "That app registration no longer exists."
- **Purpose**: Set up an iOS app: map SKAdNetwork / AdAttributionKit conversion values to goals and revenue, keep its goals, point a campaign at its App Store link, and install the SDK.
- **Data shown** (panels in this order):
  - **Breadcrumb**: "Your apps › <icon> <name> · iOS · App Store ID <key> · change (`#settings`, manager) · report" (report links to `tracking202/analyze/mobile_apps.php?registration_id=ID&platform=ios`).
  - **Conversion values** (`_ios_values.php`, anchor `#conversion-values`): a rule-count pill; empty state "No rules yet, so nothing decodes" with (manager) the button "Use starter schema"; otherwise a table Kind | Value | Goal (the event name, plus the goal's name when it differs) | Revenue (in the account currency, `dollar_format`) | Edit (`?app=ID&rule_edit=N#conversion-values`) and Remove. Rules are sorted fine values first (ascending), then coarse low, medium, high. The rules are read with `limit 200`, and a cut is not reported. Each rule's event name, goal name and revenue are derived (`PlainGoals::describe()`): the goal's event, else its name, else "goal N"; revenue is the rule's override, else the goal's fixed amount, else 0. Below, the disclosure "Account-wide default rules" (rules with `registration_id` 0), read-only with a "default" pill.
  - **Goals** (`_goals.php`, see Goals panel below).
  - **Store link** (`_link_builder.php`, see Link builder below).
  - **App token & SDK** (`_ios_sdk.php`): the app token masked (first 4 characters, bullets, last 4) with Reveal, Copy and (manager) "Rotate…"; an Info.plist snippet (`NSAdvertisingAttributionReportEndpoint` and `AttributionCopyEndpoint` set to the origin, `EligibleForAdAttributionKitReengagementPostbackCopies` true) with Copy; a Swift snippet (`P202Attribution.shared.configure(endpoint:appToken:)` with the token shortened on screen, and `logEvent("purchase")`), whose Copy puts the full token in.
  - **Recent postbacks** (newest 10 for this registration): table Received (`date('M j, H:i')` in the session's zone, `user_timezone`, else GMT) | Protocol and version | Ad network | Type | Value (the fine conversion value, else the coarse one) | Signature pill (valid good, invalid bad, development warn). Empty: "Nothing received yet". A failed read: a warning that the postbacks could not be read.
  - **Settings** panel (`#settings`): the edit form above with `return_to=app` (manager); otherwise "Changing these needs the attribution models permission."
  - **Flash messages**: `rotated=1` "App token replaced. The old token stopped working just now; apps keep their last cached schema until they fetch with the new one."; `dev=1` "Development-signed postbacks are now trusted for this app, including the ones already received." / `dev=0` the same, untrusted again; `rule=1` "Conversion value saved."; `rule=changed` a warning that devices keep the old schema for up to 7 days and postbacks arrive up to 41 days late, so until a date 48 days ahead (`gmdate('j M Y')`) a value may decode either way (`ambiguous_encoding`); `rule_removed=1` that postbacks keep decoding under the old meaning for 48 days; `starter=N` "N starter rule(s) added. Edit them to match what your app reports." or, for 0, the warning "Every starter value is already mapped, so nothing was changed."; `goal_saved`, `goal_archived`, `linked` (below).
- **Inputs**:
  - **Rule form** (manager; `action=rule_save`, hidden `registration_id`, `rule_id` when editing; a warn flash while editing): radio `kind` `fine` (default) or `coarse`; select `fine_value` 0–63 (shown for fine); select `coarse_value` low/medium/high (shown for coarse); select `goal_choice`: "A new event…" (`event`), then optgroups "This app's goals" and "Account-wide goals" (unarchived goals only, leaving out the built-in install goal and goals counted from the click, `within.from = click`); `event_name` (shown when `goal_choice` is `event`, maxlength 255, placeholder `purchase`); `revenue` (decimal text with the currency symbol, default "0.00"). Buttons Cancel, and "Save rule" (editing) or "Add rule".
  - **Starter schema** (`starter_schema`), **Remove rule** (`rule_remove`, `rule_id`, confirm: removing keeps decoding the old meaning for 48 days), **Rotate token** (`rotate_token`, confirm), **Settings** (`update`).
- **Actions**:
  - **Save rule**: `revenue`, when given, must be an amount of 0 or more with at most 5 decimal places ("Enter an amount of 0 or more, with at most 5 decimal places (for example 4.99)."); a fine rule needs `fine_value` ("Choose the fine conversion value this rule decodes (0 to 63)."). In one transaction: a numeric `goal_choice` is the goal (anything else non-numeric except `event` or blank: "Choose one of the goals listed, or a new event."); `event` or blank finds or creates a plain-event goal in the app's scope (`PlainGoals::forEvent()`: an existing goal on that event, else a new goal named after the event, or "<event> (event)" when that name is taken, with no value); a blank event "Enter the event this value means, as your app logs it (for example purchase), or choose a goal."; an invalid one "An event name is 1-64 letters, digits, _ . : or -, starting with a letter, digit or _ (for example level_up)."; then the rule is created or updated with `registration_id`, `fine_value` or `coarse_value`, `goal_id` and `revenue_override` (null when blank). API errors on `goal_id` show under the event or goal field, on `revenue_override` under revenue. Redirect `?app=ID&rule=1`, or `rule=changed` when an existing value changed meaning.
  - **Use starter schema**: six rules, each in its own transaction with its event goal: fine 1 `install`, fine 10 `trial_started`, fine 40 `purchase`; coarse low `install`, medium `trial_started`, high `purchase`. A value already mapped (409) is skipped. Redirect `?app=ID&starter=<added>`.
  - **Remove rule** → `?app=ID&rule_removed=1`. **Rotate token** → `?app=ID&rotated=1`.
- **Writes and side effects**:
  - Rules (`AppSkanEncodingsController`): `202_app_skan_encodings`; the API takes `registration_id`, `fine_value` or `coarse_value` (one of them), `goal_id`, `revenue_override`; the registration must be the account's own iOS app (or 0 for the account default); the goal must be live, owned by that registration or the account, and reachable from a device; one rule per value and registration (409 "An encoding for this conversion value already exists for this registration."). An update or delete retires the old meaning in `202_app_skan_encoding_history` with its effective time.
  - Event goals created by the rule form or the starter schema are written straight through `MysqlGoalRepository` (scope registration).
  - Rotate: a new `app_token` and `updated_at`; the old token stops working at once.
- **Edge cases and states**: the account-wide default rules cannot be edited on this page; a rule whose goal cannot be read shows "goal N"; the rule list is cut at 200 with nothing said; postback times are in the session's zone while Android install times are UTC.
- **v3 coverage**: GET /apps/{id}; GET /apps/skan-encodings?filter[registration_id]=ID (and `=0` for the defaults), POST /apps/skan-encodings, PUT /apps/skan-encodings/{id}, DELETE /apps/skan-encodings/{id}; POST /apps/{id}/app-token/rotate; PUT /apps/{id} (settings). **MISSING**: the starter schema (no route; six creates plus their goals); the find-or-create of an event goal together with its rule in one transaction (`PlainGoals::forEvent()` is not exposed: a client has to search GET /goals, POST /goals, then POST /apps/skan-encodings, not atomically). **PARTIAL**: the rule list has no event name, goal name or derived revenue (join GET /goals/{id}); the account currency for the revenue column is GET /users/{id}/preferences, which needs `access_to_personal_settings` (Campaign manager lacks it) and the account owner's id; recent postbacks are GET /apps/postbacks?registration_id=ID&limit=10, which needs `view_attribution_reports`.

### Mobile Apps: Android app page: `tracking202/setup/mobile_apps.php?app=ID`

- **Where / who**: as the iOS page, for an Android registration. Needs `access_to_setup_section`; every form needs `manage_attribution_models`.
- **Purpose**: Set up an Android app: point a campaign at its Google Play link with the install token, install the SDK and watch installs arrive, keep its goals with an install funnel, and set up Play Integrity.
- **Data shown** (panels in this order):
  - **Breadcrumb**: as iOS, with "Android · Package <key>" and the report link with `platform=android`.
  - **Store link** (Link builder below).
  - **App token & SDK** (`_android_sdk.php`): an intake strip with `<origin>/api/v3/apps/installs`, a status pill probed by the browser (`fetch` GET with header `X-P202-App-Token: <token>`; the intake answers GET with 200 `{"status":"ready"}`; same https/443 rule as the receivers, worded "Devices cannot reach this"), "Copy server URL" and Re-check; the token masked with Reveal, Copy and (manager) "Rotate…" (confirm, Android wording).
  - **Recent installs** (newest 10): table Received (`gmdate`, UTC) | Match (pill by match state, plus a test pill) | Why (the match reason; for `pending_click`, a note on settle failures) | Integrity | Click. Empty: "No installs yet", naming `p202 app install simulate ID --click N`. A failed read: a warning.
  - **Goals** (`_goals.php`), with the funnel bars below.
  - **Play Integrity** (`_integrity.php`, anchor `#integrity`): a mode pill (off, observe, require) and a description of the mode; a strip with the service account (`client_email · key <private_key_id>`, or not set), the Cloud project number, and "Decoded today" against the default quota of 10,000 a day (UTC); a table of the nonzero counts by integrity verdict ("verdict X") and by match state (`pending_integrity`, `integrity_failed`, `integrity_unverified`). A failed status read shows a warning.
  - **Settings** panel, as iOS, with the Android fields.
  - **Flash messages**: `rotated`, `dev=1` "Test installs now count for this app." / `dev=0` "Test installs no longer count for this app."; `integrity=credential` "Service account saved. Its key is stored encrypted and is never shown again."; `integrity=cleared` "Service account deleted."; `integrity=mode` "Play Integrity setting saved. Installs already received keep the mode they arrived under."; `goal_saved`, `goal_archived`, `linked`.
- **Inputs** (Play Integrity, manager, inside an Advanced disclosure remembered as `setup-mobile-apps-integrity`, open after a refused integrity form):
  - **1.
